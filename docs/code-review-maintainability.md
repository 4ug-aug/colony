## 2. The coordinator — biggest maintainability liability

[coordinator.ts](project/gui/src/server/coordinator.ts) is 2,029 lines. `createCoordinator` starts at line 298; its `async fetch` handler starts at line 595 and runs to the end. That is a **single ~1,430-line function** dispatching **36 routes**.

The shape repeats 36 times:

```ts
const issueRoute = url.pathname.match(/^\/api\/issues\/([^/]+)$/)
if (issueRoute && request.method === 'PATCH') { … }
if (issueRoute && request.method === 'DELETE') { … }
```

Consequences already visible in the file: 119 `cors(json(…))` call sites, 37 `error: 'Invalid…'` literals, and route matching interleaved with business logic so no route can be tested without standing up the whole coordinator — which is exactly why [coordinator.test.ts](project/gui/src/server/coordinator.test.ts) is 2,803 lines and calls `createCoordinator()` 35 separate times.

**Fix, in order of payoff:**

1. Extract a route table — `[method, pattern, handler]` — and dispatch with one loop. Bun's router or a 20-line matcher both work; no dependency needed. The 36 `if (x && request.method === …)` blocks collapse to 36 one-line table entries.
2. Split the handlers by resource into `routes/issues.ts`, `routes/schedules.ts`, `routes/rooms.ts`, `routes/members.ts`. Each becomes independently testable, and the 2,803-line test splits with them.
3. Make `cors` and `json` compose once at the dispatch boundary instead of at all 119 return sites.

This is the change that makes every other change in the file cheaper. It is also the one that will not happen accidentally.

### 2.1 Hand-rolled validation, duplicated per method (~130 → ~40 lines)

`POST /api/issues` ([coordinator.ts:974](project/gui/src/server/coordinator.ts#L974)) and `PATCH /api/issues/:ref` ([coordinator.ts:1087](project/gui/src/server/coordinator.ts#L1087)) validate the *same seven fields* with the *same rules*, written out twice:

```ts
// POST
if (body.tags !== undefined) {
  if (!Array.isArray(body.tags) || body.tags.some((tag) => typeof tag !== 'string'))
    return cors(json({ error: 'Invalid tags' }, 400))
}
// PATCH — identical check, then an assignment
if (body.tags !== undefined) {
  if (!Array.isArray(body.tags) || body.tags.some((tag) => typeof tag !== 'string'))
    return cors(json({ error: 'Invalid tags' }, 400))
  patch.tags = body.tags as string[]
}
```

Both paths also carry `as IssueStatus` / `as string[]` casts (10 in the file) that defeat the checks they follow.

One field-spec table — `{ tags: { check: isStringArray, error: 'Invalid tags' }, … }` — drives both create and patch, returns a typed result, and drops the casts. ~40 lines of shared code replaces ~130 lines of duplicated code. No validation library needed; this is smaller than adding one.

### 2.2 Status/priority vocabularies declared three times

`'backlog' | 'todo' | 'in_progress' | 'in_review' | 'done'` exists as:

1. a type union in [server/issue-store.ts:13](project/gui/src/server/issue-store.ts#L13)
2. a runtime array inline in [coordinator.ts:916](project/gui/src/server/coordinator.ts#L916)
3. a type union **and** `ISSUE_STATUSES` array **and** `ISSUE_STATUS_LABEL` map in [features/issues/types.ts](project/gui/src/features/issues/types.ts)

Same for priorities. Adding a status means editing five places, and nothing fails if you miss one — the validator in `coordinator.ts` just silently rejects the new value. Declare the array once, derive the type with `typeof STATUSES[number]`.

## 3. Duplication

### 3.1 Client redeclares server types verbatim (~150 lines)

`Issue`, `IssueRun`, `IssueStatus`, `IssuePriority`, `IssueOwner`, `IssueChildProgress` are byte-identical in [server/issue-store.ts](project/gui/src/server/issue-store.ts) and [features/issues/types.ts](project/gui/src/features/issues/types.ts). Same story for [features/rooms/types.ts](project/gui/src/features/rooms/types.ts) (111 lines) and [features/schedules/types.ts](project/gui/src/features/schedules/types.ts) (36 lines) against their stores.

Client and server are **in the same package** (`project/gui`). There is no bundling reason for this — `import type` is erased at build time, so the client can import the server's types directly and nothing server-side reaches the bundle. Right now the two copies can drift silently: the server adds a field, the client keeps compiling against a stale shape, and the mismatch surfaces at runtime.

Keep the label/ordering constants client-side (they're presentation). Import the shapes.

### 3.2 Identical helpers copy-pasted

- `formatBytes` — **byte-identical** in [room-timeline.tsx:127](project/gui/src/features/rooms/room-timeline.tsx#L127) and [message-composer.tsx:551](project/gui/src/features/rooms/message-composer.tsx#L551). A third, *different* implementation (binary KiB/MiB units) in [scripts/setup.ts:257](scripts/setup.ts#L257) — arguably fine, it's a different context, but the two client copies must be one.
- `formatIssueId` — identical in [features/issues/format.ts:1](project/gui/src/features/issues/format.ts#L1) and [server/issue-store.ts:145](project/gui/src/server/issue-store.ts#L145). Same package again.

### 3.3 Client fetch boilerplate, 35 times (~120 lines)

Every query and mutation repeats:

```ts
const response = await apiFetch(`/api/issues/${encodeURIComponent(issueId)}/runs`)
const data = (await response.json()) as { runs?: IssueRun[]; error?: string }
if (!response.ok) throw new Error(data.error ?? 'Unable to load runs')
return data.runs ?? []
```

38 `.ok` guards, 35 `await response.json()` casts. One helper collapses each site to a line:

```ts
async function apiJson<T>(path: string, init?: RequestInit, fallback = 'Request failed'): Promise<T> {
  const response = await apiFetch(path, init)
  const data = (await response.json()) as T & { error?: string }
  if (!response.ok) throw new Error(data.error ?? fallback)
  return data
}
```

A second helper for `POST`/`PATCH` bodies (`method`, `Content-Type`, `JSON.stringify`) removes the rest. Worth doing because it also makes error handling uniform — right now a few sites read `.json()` before checking `.ok` and others after, which behaves differently on a non-JSON 500.

### 3.4 Three near-identical pickers (~260 → ~110 lines)

[issue-property-editors.tsx](project/gui/src/features/issues/issue-property-editors.tsx) is 641 lines containing `PriorityPicker` (L125), `StatusPicker` (L197) and `OwnerPicker` (L269). All three are: `Popover` + variant-styled trigger + option list + `Check` on the selected + `mutateAsync` + success toast + error toast. They differ only in the option set, the icon component, and the label map.

One `<PropertyPicker options icon label onSelect />` covers all three. The toast pair (`success: "X updated on SWE-12"` / `error: "Could not update X"`) is repeated 8 times in this file alone and appears in 8 files overall — fold it into the mutation hook so callers stop restating it.

### 3.5 Cache-upsert logic reimplemented per feature

[use-rooms.ts](project/gui/src/features/rooms/use-rooms.ts) has private `upsert`, `mergeMessages`, `mergeRuns`, `orderedRooms`; [use-issues.ts](project/gui/src/features/issues/use-issues.ts) and [use-issue-runs.ts](project/gui/src/features/issues/use-issue-runs.ts) have `upsertIssueInCache` / `upsertIssueRunInCache` doing the same id-keyed merge-and-sort. One generic `upsertById(queryClient, key, item, sort?)` serves all of them.

## 4. Structural concerns (no quick LoC win, real maintenance cost)

### 4.1 `useRooms` is a 700-line hook

[use-rooms.ts](project/gui/src/features/rooms/use-rooms.ts) — `useRooms(userId)` spans lines 92–803 and owns: room list, selection + `localStorage` persistence, message pagination, realtime socket lifecycle, run projection, seen-message tracking, mention sound, mentionable-account lookup, and room create/delete. Every one of those is a reason to edit the same function, and none can be tested in isolation.

Split along the realtime boundary first — socket subscription and reducer separate from the query hooks. `message-grouping.ts` and `room-notifications.ts` already have their own tests and show the pattern works.

### 4.2 Provider indirection with one product each

The `providers/` layer is six files, 272 lines, to wire two real runtimes:

- `command-agent.ts` (13 lines) — one consumer, which is dead code (§1.3).
- `routing-agent-runtime.ts` (22 lines) — a two-branch `if` on `runtime.kind`, one call site ([roster.ts:255](project/agents/roster.ts#L255)).
- `openai-agents-runtime.ts` (42) and `cursor-sdk-runtime.ts` (40) — both are thin adapters over `createStdoutStepRuntime`.

`createStdoutStepRuntime` earns its keep (two consumers). The rest is a factory-per-product layer where the products are two. Once `command-agent` goes, `routing-agent-runtime`'s dispatch is small enough to live in `roster.ts` next to its only caller.

ADR 0002 and ADR 0007 justify the generic executor and explicit provider composition — that reasoning holds for `SandboxProvider` (two real implementations: Docker and Apple Container). It does not extend to the runtime factories.

### 4.3 `scripts/setup.ts` — 604 lines, one 220-line function

`configureServer` runs lines 278–500. It interleaves prompting, env-file rewriting, runtime detection, and rootless-Docker systemd overrides. The env read/write primitives (`readEnvValue`, `setEnvValue`, `encodeEnvValue`, `decodeEnvValue`) are already separated and tested — good. The prompt flow is not, and it is the part that breaks on new config keys.

### 4.4 Test setup duplication

`coordinator.test.ts` calls `createCoordinator()` 35 times across 39 tests, each rebuilding the same options object (control, store, messages, authenticator, authHandler, origin…). One `makeCoordinator(overrides)` factory removes most of the 2,803 lines' bulk. This gets much easier after §2's route split, so sequence it after.

## 5. Repo hygiene

- **`sweat-demo.mov` — 15 MB committed** ([sweat-demo.mov](sweat-demo.mov)), plus `sweat-demo.png` at 228 KB. Every clone pays for it forever; it's in history, so `.gitignore` alone won't help. Move to a release asset or the README's hosted copy.
- **`project/gui/.migration/` — 13 stale markdown files.** Per-component notes from the July 2026 `new-york` → Base UI migration ("Leftover scan: `grep -n "radix-ui"` is clean"). The migration is done; three of the notes describe components that are now dead code (§1.1). Delete the directory.
- **`.DS_Store` is tracked** — at repo root and `project/.DS_Store`. Add to `.gitignore` and `git rm --cached`.
- **Alias inconsistency.** [room-sidebar.tsx:67](project/gui/src/features/shell/room-sidebar.tsx#L67) imports `from '@/components/ui/avatar'` while all 100+ other imports use `#/`. Both resolve (`tsconfig.json` maps both to `./src/*`), so it compiles — but two aliases for one path defeats every grep. Drop `@/*` from `paths` and fix the one import.
- **Import extension inconsistency.** `ui/sidebar.tsx` imports with `.tsx` suffixes; everything else omits them. Cosmetic, but it is why a naive dead-component grep reports false positives — as this review's first pass did.
- **Docs volume.** 2,051 lines across `docs/` plus 769 in `CONTEXT.md`/`VISION.md`/`HANDOFF.md`/`README.md`. Mostly justified (14 ADRs are genuine decision records). But `HANDOFF.md` names a specific unbounded-stdout bug at `sdk/src/index.ts:25` and `runs/index.ts:252` — either that's fixed and the file is stale, or it's an open bug parked in a handoff note. Check and move it to an issue.
